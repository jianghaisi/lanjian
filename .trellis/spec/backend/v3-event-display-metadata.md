# V3 version-bound event display metadata

> Status: `verified-current` private payload/storage contract only. Authority: approved slice 2 (`09-11-v3-unified-event-projection`), design §4.3, and [event consistency](v3-planning-event-consistency.md). This is not a completed author migration, projection or UI.

## 1. Scope / Trigger

Use when serializing, validating, reviewing or reading an event version with optional legacy title and original character text. The prior explicit-field serializer discarded those fields; a source occurrence cannot safely map to a complete new version until they survive storage. This increment uses the existing immutable JSON payload, **not** new columns, a separate display authority or a schema change. It originally landed on schema 39; the separate [receipt storage increment](v3-event-migration-receipts.md) advances current schema to 40 without changing display serialization or existing absent-field payload hashes.

## 2. Signatures

```ts
type StoryEventDisplayMetadata = { title?: string; rawCharacters?: string }
type StoryEventContent = StoryEventDisplayMetadata & {
  time: string; characters: string[]; location: string; event: string; result?: string
  evidenceRefs: Array<{ sourceId: string; excerpt: string }>; confidence: number
}
assertStoryEventDisplayMetadata(value: unknown):
  asserts value is StoryEventDisplayMetadata & Record<string, unknown>
assertStoryEventVersionPayload(value: unknown): asserts value is StoryEventVersionPayload
storyEventVersionPayload(value: StoryEventVersionPayload): StoryEventVersionPayload
```

The domain owner is `desktop/src/main/modules/timeline/domain/story-event-version.ts`. The existing `CanonicalEventVersions.append/decode` and the existing source snapshot consume this contract without new storage methods. `event-migration-review.ts` calls the same metadata validator before splitting a direct row's character string, and includes both fields in its validation-only probe. No new environment key, IPC/preload DTO, renderer input or author authorization is introduced.

## 3. Contracts

### Exact values and historical compatibility

| Field | Bound and meaning |
| --- | --- |
| `title` | Optional string, at most 200 JavaScript UTF-16 code units; may be empty/whitespace; NUL rejected |
| `rawCharacters` | Optional string, at most 20,000 UTF-16 code units; exact original/display character text, may be empty/whitespace; NUL rejected |
| `characters` | Existing required ordered name array remains independent: 1–100 nonblank names, each at most 200 code units |

Missing or `undefined` optional fields are omitted entirely; `''` is present and distinct. Null, arrays, numbers and objects are not coerced. Do not trim, truncate, normalize Unicode, sort/deduplicate names, synthesize raw text from the array or parse raw text during version serialization. New fields do not relax time/place/event, material/source, phase, granularity or author/candidate constraints.

The serializer preserves the old field order and appends `title`, then `rawCharacters`, after `confidence` only when present. Existing payloads with neither field therefore retain **exact JSON bytes and SHA-256**, including absent/empty/nonempty `result`. Caller property order cannot affect serialization. Title/raw-character/result-only changes affect the complete version payload hash, even though the old four-field suggestion signature can remain identical. Neither hash equality nor a signature grants event identity or merge permission.

The existing immutable version JSON, hash, source seals and heads are the storage authority. No migration rewrites historical JSON or synthesizes metadata for old records. Historical payloads generated by the old serializer have these fields absent. If an externally modified historical payload contains a malformed newly recognized field, the reader fails closed even if its hash was recomputed; it does not repair or silently drop it. Unknown unrelated metadata remains original source evidence, not automatically part of the selected version fields.

### Review, writes and reads

- Direct review converts only the **field name** from source `characters: string` to validation-probe `rawCharacters`; its bytes stay retained unchanged. The proposal still splits only visible separators, never Chinese conjunctions, and does not commit the proposed name array. The shared metadata validator runs first so oversized raw text is rejected before splitting. A valid direct record still needs author review, provenance and destination/link checks.
- `appendCanonicalEventVersion` is an internal full-payload operation, not a metadata PATCH. A caller retaining display fields must carry the selected content forward; deliberately omitting them creates a new absent-field version. Never backfill earlier versions or infer an author's removal intent from a lossy legacy DTO. Future UI/writer routing must present and bind the full selected version before allowing that choice.
- Existing transaction/source checks remain at their owner. Metadata does not authorize cross-book access, new sources or candidate approval. A metadata-only candidate advances only the latest head and leaves the approved head and compatibility mirror unchanged.
- Existing canonical rows and readable compatibility event JSON have no title/raw-character fields. They remain their limited legacy projection; they cannot reconstruct the new fields or replace immutable version content. This checkpoint does **not** connect unified timeline/map/generation consumers or make a unified mirror.
- Same-pinned-source acquisition retains full version metadata, includes it in the existing history fingerprint and freezes it with the snapshot. Read-only acquisition never adds missing metadata, rewrites a mirror or upgrades schema. A newer metadata-only candidate changes this all-source fingerprint without becoming approved.
- Bare author versions can have empty material evidence under the existing version contract. The legacy canonical migration inspector still requires material evidence and can flag such a record. This checkpoint does not claim that inspector is ready for unified-author histories; module routing and reviewed migration remain required.

### Runtime type boundary

Keep the `Record<string, unknown>` intersection on the metadata assertion. Narrowing a broader record to only the optional metadata type can hide the other content members from TypeScript. Validate those existing fields independently; do not cast through `any` or suppress the compiler to work around the problem.

## 4. Validation & Error Matrix

| Condition | Outcome |
| --- | --- |
| Valid absent/empty/Unicode display values | Exact optional values round-trip; old absent payload hash unchanged |
| Non-record input, wrong type, NUL or over-limit display text | Safe `VALIDATION_ERROR`; no coercion/truncation/write |
| Valid display fields but invalid required names/source/phase/creator | Existing validation rejection remains |
| Stale expected latest head | `CONFLICT`; no partial event/version/mirror rows |
| Cross-book event or missing source revision | Existing `NOT_FOUND` / `CONFLICT`; no new authority |
| SQL failure after version insertion | Existing safe `STORAGE_ERROR`, internal cause retained; full transaction rollback |
| Direct UPDATE/DELETE of stored display history | Append-only SQL guard rejects |
| Changed stored display value without matching hash, or malformed value with a matching hash | `DATABASE_INTEGRITY_FAILED`; no fallback, repair or original-file write |
| Legacy source cannot fit metadata/name bounds | Retained invalid occurrence, not clipped content or a partial migration |

## 5. Good / Base / Bad Cases

- Good: `rawCharacters: '  归与、和光；林及舟 / 和田\r\n归与  '` survives unchanged; review proposes an ordered array retaining the repeated name and does not split 和/与/及.
- Base: old version lacks both fields; a new version has both empty; reopening distinguishes them and leaves the old payload/hash exact.
- Bad: fill an old title from today's map, join a name array to invent original text, hash `title || ''`, or approve a candidate because its title was edited.

## 7. Wrong vs Correct

```ts
// Wrong: loses absence and changes old hashes; invents original character text.
// content.title = source.title || ''
// content.rawCharacters = content.characters.join('、')
// UPDATE canonical_event_versions SET payload_json = ...

// Correct: only selected optional values participate, with no historical rewrite.
const content = {
  ...selectedVersion.content,
  ...(source.title !== undefined ? { title: source.title } : {}),
  rawCharacters: source.characters
}
assertStoryEventDisplayMetadata(content)
// The existing internal full-version writer still needs current identity/revisions
// and trusted reviewed authority; constructing this object does not grant consent.
```

Source aliases and immutable receipt/module-marker tables now have a separate schema-40 structural contract; no production writer or reader publishes them yet. Lifecycle/order, reviewed decisions/token/transaction, unified consumers/mirrors and typed desktop operations are still outstanding. All slice-2 ACs remain open; metadata persistence alone is not lossless migration completion.
