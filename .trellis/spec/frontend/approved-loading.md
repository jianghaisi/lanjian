# Author-approved loading themes (2026-09-08)

## Current V3 companion startup override (2026-09-12)

This narrow reuse is accepted by `09-11-v3-companion-local-voice-and-safe-dialogue`, not blanket approval of all historical UI. It supersedes the older no-skip and AppShell-owned completion paragraphs below only for application boot; work-opening behavior is unchanged.

1. **Scope / trigger:** application start with optional saved companion preload; reuse both existing themes, native visibility gate and 3-second scan completion.
2. **Signatures:** `AppBootScreen` accepts `phase: projects|editor|session|models|ready`, `detail`, `modelsRequired`, `canSkipModels`, existing error/preview/theme/motion props; emits `complete`, `skipModels`, `retry`, preview `skip`, and visual readiness. `useCompanionBoot(corePhase,coreError,preview)` supplies the derived state. `useBootCompletion(ready,complete)` is the sole completion timer owner. Main reuses the existing no-payload `app:window-shown` notification; no new renderer command, payload or persisted visibility flag.
3. **Contracts:** when `preload && (textModel || !mute)`, wait for the library-owned real warmup result. Only visible `ready && !error && !preview` starts 3000ms; losing readiness/unmount cancels stale timers. Ready has distinct check/text/contrast and a “现在进入” action independent of animation readiness. Main sends the existing signal on the owned window's `show`, `restore` and `webContents.did-finish-load`, only while that window is alive/visible and its web contents alive. This replays truth to a reloaded preload without consuming hidden startup time; renderer handling stays idempotent. Skip only model waiting, never core initialization; do not persist it, fake model-ready rows or cancel a pending background warmup. No-models/on-demand modes omit model readiness. Preview remains visual-only. Reduced motion disables displacement but retains ready/entry controls and the 3-second completion interval. Ordinary boot and sound settings must not explain animation mechanics or show an animation countdown; preview retains its non-initializing disclaimer.
4. **Validation / errors:** core failure → retry only; warmup failure → retry or explicit skip; disabled modes → no wait; hidden native window → no automatic countdown; shown-window reload → replay actual visibility and complete; missing animation signal after real ready → manual entry remains usable; skipped failed preparation → not-ready wording, not a background-running claim.
5. **Cases:** good = real profile preparation then 3 seconds of visible completion, including after an already-shown window reload; base = presets with no model stage; bad = fixed startup timeout/installed-file check claiming model readiness, or a ready screen with both completion and entry blocked by a lost one-shot event.
6. **Tests:** `companion-boot-completion.test.ts`, `loading-terminal.test.ts`, `companion-boot-smoke.mjs`, native speech-only startup smoke; retain `loading-terminal-smoke.mjs` for theme, narrow layout, preview and hit targets. `boot-reload-smoke.mjs` must wait for the FIRST native show before reloading, then prove repeated reload auto-entry, hidden reload waiting for real show, and manual entry. Component tests withhold the native signal and still click ready entry. Assert normal boot has no animation-mechanics note; inspect loading, ready, entered and failure screenshots. Use isolated profiles, not author preferences or works.
7. **Wrong / correct:** wrong `initializeBoot -> sleep(3000) -> hide` while model job is pending; correct single library warmup → derived ready → visible component completion timer → `complete` event. Wrong `readyToEnter = actualReady && motionReady`; correct `readyToEnter = actualReady`, `readyToAnimate = readyToEnter && motionReady`. A one-shot `ready-to-show` event does not survive a renderer reload: replay native truth rather than guessing from DOM visibility or adding a timeout that pretends the window is visible. No OS-startup service or second worker owner.

## Historical reference contracts

- The author supplied **two** HTML references, each with boot/open-work scenes. Keep both `standard` and `impact`; do not infer a third theme from older conversation.
- Source archives live under `design-system/approved-2026-09-08/`. Production uses `AppBootScreen` and `WorkspaceLoadingScreen`, not their demo pages, screenshots or iframes.
- Theme and motion preference are appearance-only local state (`lanjian-loading-v1`). An absent preference and an explicit reset use `impact` as the product default; a valid saved `standard` choice remains respected. Storage failures must remain visible, invalid bytes preserved; explicit reset backs up before replacement. No project paths, prose or model credentials belong in this preference.
- Actual lifecycle drives phase labels, completed state, derived progress and teardown. Source demo timers, time-based percent counters, fake editor text and automatic AI-ready claims must not enter production. The orange scan remains a vertical line moving linearly left-to-right and patrols only the horizontal `5% → current lifecycle progress` range. A phase change preserves the currently painted position and updates the linear target without restarting keyframes. At 100%, app boot takes three seconds from the current position to reach the viewport's right edge; the work loader keeps its one-second completion movement. AppShell mounts the opaque work loader immediately on selection, without an entry fade or a 300ms visibility threshold, so partially initialized writing UI cannot flash beneath it.
- The work loader may visually lag a real forward phase jump to preserve sequential feedback. Once visible, AppShell presents every crossed phase in order, waits until that phase has reached a browser paint, then holds it for at least 320ms; this playback never changes the underlying lifecycle result, and the one-second ready handoff begins only after visual playback reaches `ready`. Phase emphasis may fade opacity but must not translate the list row. Reduced motion snaps directly to the real phase, and cancellation must not wait on decorative playback.
- During that visible one-second work-opening completion, the dark dossier block clears its content and morphs onto the real writing sidebar geometry: the 72px primary rail plus the current saved explorer width, between the 48px title bar and 24px status bar. This is transient UI only and must not persist a second layout preference.
- The work-loading title mark uses the first five non-whitespace Unicode code points of the current work title without an ellipsis. It sits in the lower background layer of the right-hand progress region, where foreground progress modules may cover it. Responsive type keeps it bounded inside that region so it never extends beneath the dark dossier panel or creates horizontal overflow. The complete title remains available in the dossier content.
- The two inner boot orbits rotate continuously with distinct constant angular velocities. They remain ambient background motion and stop under either reduced-motion path.
- Normal application startup always presents the boot loader and exposes no skip/hide control or persistent disable preference. A boot preview may retain an explicit close action; a failed real initialization offers retry rather than bypassing incomplete startup. The isolated Electron smoke query may suppress the real startup overlay, but this is test-only, not persisted and not exposed in product UI.
- Electron creates its window hidden until `ready-to-show`; boot CSS animations and the JavaScript progress-line transition therefore remain paused until the main process explicitly signals that `BrowserWindow.show()` has run. `AppBootScreen` emits visual readiness only after that native window signal, and AppShell starts the three-second successful handoff from the same point. DOM `visibilityState` alone is insufficient because Electron may report `visible` for a hidden BrowserWindow. Hidden-window time must never consume the orange impact slash or successful completion hold.
- Loading motion style and application colour theme are independent axes. Both boot and work loaders inherit the resolved `qingzhou`, `xuanzhi`, or `moye` theme for canvas, text, dividers, dossier surfaces, orbit/grid artwork and accent treatment; switching between `standard` and `impact` must not discard that app-theme palette. Validate dark-theme contrast independently.
- Library settings is a native `<dialog>`. A body-teleported fixed preview cannot reliably appear above the native top layer. `LoaderPreferences` uses its own `showModal()` dialog, then focuses its close button; native Escape closes and restores the originating preview button. Keep close controls hit-testable in the viewport.
- `LoaderPreferences` is exposed from the library appearance dialog only. Do not duplicate loading-animation controls inside an opened project's Settings page.
- Both themes honor `prefers-reduced-motion` and the local motion switch. Reduced motion skips the boot/work completion hold and all scan/morph displacement. Animated nodes must already have visible non-animated base styles. Omit intense repeated/full-screen flashes; preserve distinct scan/dossier vs cut/stamp behavior.
- Test phase semantics and storage with `loading-terminal.test.ts` and `loading-preferences.test.ts`; additionally exercise selection, both previews, Escape/focus and persisted reload through real Electron clicks. Unit/SSR success is not screenshot acceptance.
- `approved-loading.css` owns viewport sizing for both components: logical 100dvw/100dvh, clipped roots and bounded content rows. Preview dialog also clips rather than scrolls. Transformed aria-hidden orbit artwork can increase scrollWidth despite `overflow:clip`; this does not prove a scrollbar. Assert root bounds, actual inability to scroll, no overflowing auto/scroll descendants, visible/unclipped phase content and actual close hit targets together.
